# Архитектура: план работ

Цель: у каждой стратегии свой тест-паспорт, где зафиксирована конфигурация, выбранная в исследованиях (с номером
исследования V…), и проверено, что код с этой конфигурацией ведёт себя как в исследовании. Сюда же: покрытие строк
кода тестами, код без повторов, у каждого модуля одна ответственность.

Правила работы (как в раунде 1):
- сначала тесты на текущее поведение, потом переработка; после неё те же проверки зелёные без изменений;
- маленькие шаги, каждый шаг — свой коммит; в прод — только после OK пользователя, деплой проверяется по событиям в базе;
- менять поведение торговли можно только явно, с записью в коммите и с OK пользователя.

### Шаг 4. Конфигурации — в коде, с паспортом
Для каждой стратегии `Params::RESEARCH` (константа) = выбранная конфигурация; env оставить только для выключателей
(`*_ENABLED`) и секретов (правило «config in code»). Тест-паспорт стратегии:
1. **конфигурация**: значения `Params::RESEARCH` = таблица ниже (изменение без обновления паспорта — красный тест);
2. **паритет с исследованием**: правило на фикстуре свечей (выгрузка из исследовательских данных) даёт ровно те сигналы,
   что и исследовательский код (как breakout: 93 из 93 на 11 монетах) — фикстура и ожидаемые сигналы лежат в

### Шаг 5. Инфраструктура под тестами
- `store`: запись событий и документов — тест на файлах и на Postgres (локальный Postgres в тесте, если доступен;
  иначе трейт `EventSink`, Postgres-реализация тонкая);
- `api`, `ws`, `notify`: через фейковый HTTP/WebSocket сервер (книги, миды, Telegram);
- `clusters`, `micro`, `walls`, `wickwatch`: правила — чистыми функциями, запись — через `EventSink`;
- `main.rs`: только сборка зависимостей и запуск; e2e-тест старта на фейке (все стратегии стартуют, первые шаги идут).
